SOC Homelab

A multi-VM Security Operations environment built on Proxmox VE for hands-on detection, log analysis, and incident response practice.

Proxmox VE Splunk Enterprise Sysmon Windows 10 Ubuntu Server Kali Linux Hydra SPL Alert Triage

Objective

Build a realistic SOC environment from scratch to practice the skills required for a Security Operations Center Analyst role — log ingestion, endpoint telemetry, alert triage, and detection engineering — without relying on simulated cloud labs.

Architecture

The lab runs on a dedicated physical machine using Proxmox VE as the hypervisor, with VMs segmented into a isolated lab network separate from management traffic.

Windows 10 Endpoint

Primary target machine. Generates Windows Event Logs and Sysmon telemetry forwarded to Splunk via Universal Forwarder.

Ubuntu Server

Linux endpoint running Splunk Universal Forwarder to ship syslog and auth logs into Splunk for centralized Linux visibility.

Splunk Enterprise

Central SIEM receiving logs from all endpoints. Used for log search, investigation, and detection rule development via SPL.

Kali Linux

Attacker VM on the isolated lab network used to simulate adversary techniques — port scanning, SSH brute force — and validate detection coverage in Splunk.

What Was Built

  • Network Segmentation — Lab traffic isolated from management access via separate Proxmox network bridges, preventing cross-contamination between attacker and management interfaces.
  • Splunk SIEM Deployment — Splunk Enterprise installed and configured with Universal Forwarder on all endpoints to centralize log ingestion. SPL queries used to validate and search telemetry across Windows and Linux hosts.
  • Sysmon Tuning — Deployed Sysmon with the SwiftOnSecurity configuration to capture process creation (Event ID 1), network connections (Event ID 3), and file I/O events (Event ID 11) for high-fidelity endpoint visibility.
  • Linux Log Forwarding — Configured Splunk Universal Forwarder on Ubuntu Server to ship syslog and auth.log into Splunk with correct sourcetype configuration for proper field extraction.
  • Windows Event Log Coverage — Enabled and verified Windows Security, System, Application, and Sysmon/Operational logs flowing into Splunk for layered endpoint visibility.
  • Attack Simulation — Deployed Kali Linux attacker VM and ran port scan (nmap) and SSH brute force (Hydra) simulations against lab endpoints. Analyzed resulting artifacts in Splunk to understand what each attack technique generates in logs and where coverage gaps exist.
  • Detection Rule Development — Built three scheduled SPL detection rules from real attack data (inbound port scan, SSH brute force, and successful-login-after-brute-force correlation), all validated end-to-end against live attack traffic and confirmed firing in Splunk Triggered Alerts.
  • Alert Triage Runbook — Documented a general triage workflow plus per-rule triage steps for each detection, covering enrichment, validation, and escalation decisions.
  • Enumeration Simulation — Ran SMB enumeration attempts from the Kali VM against the Windows endpoint under both default and deliberately opened firewall configurations to compare attacker visibility.

Detection Rules

All three rules are scheduled in Splunk, trigger on results > 0, and were validated end-to-end by running the corresponding attack simulation and confirming the alert fired in Triggered Alerts.

1
Port Scan Detection — Inbound WFP

Detects inbound port scans against the Windows endpoint by monitoring Windows Firewall (WFP) blocked connection events (EventCode 5157). Triggers when 3 or more unique destination ports are blocked from a single source IP within a 60-second window. Multicast traffic excluded to eliminate SSDP noise. Threshold set to 3 based on empirical observation that a full 1000-port nmap scan only generated 6 WFP events — WFP logs only ports matching firewall filter rules, not silently dropped packets.

2
SSH Brute Force Detection — linux-logsource

Detects SSH brute force attempts against the Linux endpoint by monitoring auth.log for failed password events. Uses SPL regex extraction to parse source IP and username from raw log lines. Triggers on 5 or more failed login attempts from a single IP within 60 seconds. Also tracks unique usernames targeted to distinguish credential stuffing (many usernames) from targeted brute force (one username, many passwords) — context that helps an analyst assess severity during triage.

3
Probable Compromise — SSH Success After Failed Attempts

Upgrades a brute-force alert into a probable-compromise alert by correlating a successful SSH login with recent failed attempts from the same source IP. Uses SPL streamstats with a rolling 10-minute lookback window per source IP, rather than a fixed time bucket, so the failed-attempt count stays accurate regardless of where the success lands relative to bucket boundaries. Set to Critical severity — the highest of the three rules — since it fires on a probable successful compromise rather than just an attempt. Live-tested against a real brute-force-then-login sequence from the Kali attacker VM and confirmed firing correctly.

Alert Triage Runbook

Built a structured triage runbook covering the general analyst workflow — acknowledge, enrich, validate, decide, act, document — plus per-rule triage steps for each detection above: pivoting on the source IP, correlating across Windows and Linux logs, and distinguishing a real threat from noise before escalating.

Enumeration Simulation — SMB

Ran an SMB enumeration simulation from the Kali attacker VM against the Windows endpoint (nmap SMB NSE scripts, smbclient, enum4linux). Baseline (default hardened config) showed Windows Firewall silently blocking inbound SMB entirely. Deliberately opened the SMB path to compare results: port reachable, but anonymous/null-session SMB authentication was still rejected by default — NetBIOS host info leaked via NBT-NS (a separate, unauthenticated protocol), but no share or user enumeration was possible. A concrete, realistic finding: a properly hardened Windows host resists SMB recon even when the port itself is reachable.

Key Troubleshooting — Hostname Mismatch

During initial setup, Windows endpoint data was not appearing in Splunk as expected. Rather than redeploying the forwarder immediately, a structured troubleshooting approach was used:

1
Ruled out network connectivity

Verified the Universal Forwarder could reach the Splunk indexer on port 9997. Connectivity was confirmed — not the issue.

2
Ruled out configuration errors

Checked inputs.conf and outputs.conf on the forwarder. Configuration was correct — not the issue.

3
Identified root cause — hostname mismatch

Data was arriving in Splunk but indexed under an unexpected hostname. The Windows VM hostname did not match the expected value in the SPL search filter, causing the data to appear missing when it was actually present under a different host value.

This troubleshooting process mirrors real SOC investigation methodology — rule out the obvious before assuming the complex.
